# Cascade Control Overlay (`cco`)

> **[English documentation (README.md)](README.md)**

**Cascade Control Overlay** — открытая высокопроизводительная реализация на языке **Rust** программного комплекса диссертационного исследования (специальность **2.3.6 «Методы и системы защиты информации, информационная безопасность»**, автор — Зюзин Владислав Дмитриевич).

Проект реализует архитектуру гибридной маршрутизации виртуальных частных сетей, разделяющую **многоскачковую защищённую доставку установочного обмена** (control plane) и **прямую передачу пользовательских данных** (data plane) без модификации конечных VPN-протоколов (**IPsec/IKEv2** и **WireGuard**).

---

## Ключевые компоненты комплекса

1. **Алгоритм множественных стартовых соединений (МСС / MCC, Глава 2.1):**
   - Каскадное ветвление эквивалентных копий установочного обмена по схеме `A -> X1 -> X2 -> B` с бюджетом `(x1_fanout, x2_fanout, ike_fanout)`.
   - Четыре режима отбора ветви на получателе `B`: `first`, `window`, `adaptive` (`min_copies`, `quiet_ms`) и `wait-all`.
   - Сквозная аутентификация копий подписями `Ed25519` (`verify_strict`), пошаговая конфиденциальность капсул `X25519 + HKDF-SHA256 + AES-256-GCM`, непрозрачные маркеры продолжения (`opaque_token`, инициатор `A` не узнаёт выбранный узел `X2`), одноразовый токен доставки `LocalDeliveryProof` (move-only в Rust) и долговременный SQLite anti-replay журнал (семантика at-most-once).
2. **Оверлейный управляющий канал для IKEv2 и WireGuard (Глава 2.2):**
   - Прозрачный перехват только управляющего обмена: **IKEv2** (`IKE_SA_INIT`, `IKE_AUTH` на UDP/500 и UDP/4500 с Non-ESP Marker `00 00 00 00`) и **WireGuard handshake** (`type 1/2/3`, жёсткий запрет на попадание `type 4` Transport Data в оверлей).
   - Прямой выход защищённого пользовательского трафика (**IPsec/ESP** или **WireGuard `type 4`**) между конечными узлами.
   - Linux-адаптер (`cco-linux-proxy`) на базе `nftables`, `IP_TRANSPARENT`, `IP_RECVORIGDSTADDR`, `SO_MARK` (`0x53`), `SOCK_RAW` (`IP_HDRINCL`) и обхода `ip xfrm policy`.
3. **Обобщённый H-скачковый приватный каскад (`UniversalCascade`):**
   - Чистая Sans-I/O state-машина для произвольной глубины `H >= 2` (`CASCADE_BUILD..CASCADE_CLOSE`), локальная изоляция ячеек `RelayCell`, обход при `CASCADE_REJECT` и пересборка при `CASCADE_ABORT`.
4. **Аутентифицированный реестр доверенных узлов (`Trust Registry v2`):**
   - Схема `ipsec-ike-cascade-trust-registry/v2`: раздельные ключи `X25519` (шифрование) и `Ed25519` (подпись) на каждый узел, внешний закреплённый корень доверия (`pinned root`), строгий парсинг JSON без дубликатов, монотонный антиоткатный счётчик версий, атомарное обновление (`fsync + rename`) и восстановление `last-valid`.
   - Режим fail-closed: узел не открывает UDP-сокет без пройденной криптографической проверки реестра. Любые парольные fallback-механизмы полностью исключены.
5. **Аналитический и Монте-Карло движок (Главы 3 и 4):**
   - Точная арифметика большой разрядности (`BigUint`) для расчёта пространства маршрутов (`F1/Tor`, `I2P`, модель `F3` без повторений, модель `F4` с несмежными повторениями и транзитным участием конечной пары).
   - Расчёт вероятности компрометации маршрута, точного порога размера сети `n50` (например, `m=2, j=5`: `n50(F4) = 17` против `n50(F1) = 20`, сокращение требуемого пула на 15 %).
   - Многопоточная верификация Монте-Карло на `rayon` (`800 000` маршрутов на модель за ~2 мс с отклонением от аналитики `<= 0.0004`, что на порядок строже допуска `<= 0.004` из п. 4.4 диссертации).

## Архитектура Cargo Workspace

Во всех крейтах действует `#![forbid(unsafe_code)]`, кроме `cco-linux-proxy`, где `unsafe` изолирован в минимальных Linux syscall-обёртках (`setsockopt`, `recvmsg`, `sendto`). Используется только проверенная криптография RustCrypto/dalek с `Zeroize`/`ZeroizeOnDrop`.

```text
cascade-control-overlay/
├── crates/
│   ├── cco-crypto/        # X25519, HKDF-SHA256, AES-128/256-GCM, Ed25519, Zeroize
│   ├── cco-trust/         # Trust Registry v2 (pinned root, anti-rollback, atomic store)
│   ├── cco-proto/         # Wire-сообщения, LinkFrag (<= 1200 B), парсеры IKEv2 и WireGuard
│   ├── cco-cascade/       # Sans-I/O ядро: MCC + SQLite ledger, UniversalCascade, WG 27-matrix
│   ├── cco-transport/     # Async Tokio UDP mesh, 4-шаговый MGMT, неблокирующий воркер сессий
│   ├── cco-linux-proxy/   # Linux TPROXY / SO_MARK / RAW inject + генератор nftables/xfrm
│   ├── cco-analytics/     # Комбинаторика Главы 3, n50, rayon Монте-Карло, бенчмарк Таблицы 4.6
│   └── cco-cli/           # Единый CLI-бинарник `cco`
├── lab/                   # Лёгкий Docker (~200 МБ) и автономный Linux ip netns стенд strongSwan
├── examples/              # Безопасные примеры конфигураций (только RFC 5737)
└── docs/                  # Архитектура, спецификация протокола, модель угроз, бенчмарки
```

## Быстрый старт

```bash
# 1. Прогон всех тестов (L1 + L2 localhost UDP E2E + Rust<->Python wire cross-compat)
cargo test --workspace

# 2. Проверка примера подписанного Trust Registry v2
cargo run --release -p cco-cli -- trust-admin verify \
  --registry examples/trust-registry.example.json \
  --trust-root examples/trust-root.example.json \
  --required-nodes A,X1,X2,B

# 3. Расчёт пространства маршрутов и вероятности компрометации (n=10, m=2, j=3)
cargo run --release -p cco-cli -- analytics routes --n 10 --j 3 --m 2

# 4. Расчёт порога n50 (m=2, j=5 -> F1=20, F3=18, F4=17)
cargo run --release -p cco-cli -- analytics n50 --m 2 --j 5

# 5. Бенчмарк криптографии Таблицы 4.6 (X25519+HKDF+AES-GCM против RSA-3072 OAEP)
cargo run --release -p cco-cli -- bench crypto --iters 200 --rsa-iters 20 --include-rsa

# 6. Каноническая матрица 27 сценариев WireGuard Handshake Overlay
cargo run --release -p cco-cli -- wg-sim --format csv
```

### Живая L3-проверка со strongSwan на Linux / WSL2 (без создания ВМ EVE-NG)

```bash
cargo build --release -p cco-cli
sudo CCO_BIN=./target/release/cco bash lab/scripts/netns_e2e.sh
```

Скрипт поднимает 5 изолированных сетевых пространств имён Linux (`cco-isp` с мостом `cco-br0` и `tcpdump`, `cco-A`, `cco-X1`, `cco-X2`, `cco-B`), применяет правила `nftables`/`xfrm`, запускает 4 узла `cco node` и два немодифицированных демона `strongSwan charon`, устанавливает IPsec-туннель `198.51.100.10/32 <-> 198.51.100.13/32`, прогоняет ICMP-трафик и автоматически проверяет pcap:
- `direct_ike_total == 0` (ноль прямых пакетов IKEv2 между `A` и `B` на мосту провайдера);
- `overlay_udp_packets > 0` (324 пакета защищённого оверлея на UDP/9000);
- `direct_esp_proto50 == 10` (прямой IPsec ESP, 5/5 ICMP-ответов, 0% потерь).

## Честные границы применимости

- Комплекс является **исследовательской open-source реализацией** алгоритмов диссертации и не проходил независимый внешний криптографический аудит.
- Модель угроз покрывает наблюдение за прямым управляющим обменом на участке провайдера и скомпрометированные/подменяющие пакеты промежуточные узлы (honest-but-curious и активная подмена на релеях обнаруживается криптографически).
- Архитектура **не защищает** от глобального пассивного противника, контролирующего все каналы и выполняющего временную корреляцию, и **не скрывает** последующий прямой обмен защищёнными данными IPsec ESP / WireGuard между `A` и `B`. Подробнее: [SECURITY.md](SECURITY.md) и [docs/THREAT-MODEL.md](docs/THREAT-MODEL.md).
